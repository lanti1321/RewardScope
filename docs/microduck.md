# MicroDuck 项目接入与诊断

[返回项目说明](../README.md)


默认首页 <http://127.0.0.1:8765> 或 `/microduck` 是 MicroDuck 工作台。官方代码保存在 `upstream/microduck_rl`，固定于提交 `cb70b792312d559a4da09064d92009079671815f`，Apache-2.0 许可证原样保留。上游的代码和锁文件没有修改。

界面按「项目概览 → 环境与奖励 → 训练监控」组织。首页展示已接入项目；配置页读取官方任务的控制频率、回合时长、观测组、终止条件、课程项和奖励函数。左侧保留历史训练记录，点击后进入该次训练监控。当前没有任意项目一键导入，其他 RL 项目需要对应适配器。

首次安装官方环境：

```bash
bash setup.sh
bash setup_microduck.sh
bash start.sh
```

官方运行环境独立于工作台的 SB3 环境，使用 Python 3.12、mjlab 1.3.0、MuJoCo 3.10.0、Warp 1.12.0、PyTorch 2.9.1 和 RSL-RL 5.0.1。此上游提交的 manifest 与锁文件校验存在漂移，因此安装使用 `uv sync --frozen` 保留官方锁定版本，避免重新解析升级。

工作台从官方任务注册表生成任务与奖励目录。默认 `Mjlab-Velocity-Flat-MicroDuck`：64 个环境，5 次 PPO 迭代，每环境每次迭代 24 步，共 7,680 次环境交互。**这个预算只验证运行链路，不足以学会行走。** 可直接设置更大预算，不检查是否存在历史测试记录。首次 GPU 内核编译可能需要几分钟。

### 适配方式

- `microduck_bridge.py` 在官方虚拟环境中调用官方 `TrainConfig.from_task`、`run_train` 和任务注册的 runner，保留官方 PPO、BAM 执行器、观测归一化、域随机化、终止条件与课程。
- 默认只改变并行环境数、训练迭代数、随机种子、运行名称与本地日志设置；使用 TensorBoard，关闭 W&B 上传。不发起云训练，也不连接实体机器人。
- 奖励设置仅支持数值权重和独立屏蔽开关，不修改触发条件或函数。未编辑项沿用课程当前权重；编辑项使用固定权重，覆盖该项课程权重；屏蔽优先级最高，始终使用零权重。计算后恢复管理器原权重供官方课程继续运行。单项“恢复”或“恢复官方设置”取消固定权重与屏蔽。设置随本次训练保存；旧记录中的倍率配置仍可读取。
- 在官方 `reward_manager.compute` 后、自动重置前采样环境 0；记录真实动作、qpos、终止标记、当前奖励权重与分项，并由官方 MuJoCo 渲染器生成同一步图像。
- 单步奖励分项包含 `dt` 缩放，运行时检查各项之和与实际奖励一致。`Episode_Reward/*` 是官方的时长归一化聚合日志，界面单独标明，不能与单步奖励混用。
- 新训练的画面按墙钟时间最高 2 帧/秒更新，只渲染环境 0；原子覆盖 `latest.json`，不保存历史图片。浏览器单次请求完成后才允许下一次请求，隐藏页面不请求预览。暂停或优化阶段可能不更新，界面显示画面采集时间。
- 奖励数据仍按 `max(4, ceil(iterations × steps_per_iteration / 400))` 稀疏采样，最多约 400 组数据。滑块回看这些历史数据，不回放最新画面；两者时间不保证一致。旧记录仍可回看已有图片。
- 官方 reward/termination 所读的某些派生状态本就滞后一个物理子步；适配器不改这个上游语义。MuJoCo 画面根据该采样时刻的 qpos 重建。
- 原始日志、环境与算法 YAML、checkpoint `.pt` 和官方 runner 导出的 ONNX 均保留在实验目录。官方导出包含观测归一化；适配器不手工转换策略。

保存位置：`runs/microduck/<实验 ID>/`，包含 `run.json`、`train.log`、`frames/*.jpg` 和 `official/`。JSON 导出含数值采样记录，图像与模型需通过对应下载或复制整个目录保存。暂停和继续只用于存活的进程，停止会保存当时模型；服务重启后不自动续训。

目录中列出的官方任务不代表全部已在本机训练验证。当前重点验证平地行走基线；其他任务仍需各自的小规模测试。该版本还没有独立多种子机器人评估、训练后确定性策略回放、已有 checkpoint 续训界面或实机部署功能。

### 内部诊断与自动发现（v0.4）

- 项目概览可重新扫描官方项目：不执行代码的 AST 扫描列出候选定义及行号，运行时解析官方任务注册表，自动读出奖励函数来源、初始权重和 Actor/Critic 默认结构。静态候选不代表已确认的训练执行路径。
- 通用扫描器可独立使用：`.venv/bin/python -m rl_workbench.discovery /path/to/project`。它不导入目标项目，跳过虚拟环境、生成目录和符号链接；扫描上限 3000 个 Python 文件。运行时自动解析目前仍仅接入 mjlab / RSL-RL 的官方项目。
- 配置页支持修改已识别 MLP 的隐藏层：Actor、Critic 各 1–6 层，每层 8–1024。变更保存到本次训练配置，官方 runner 创建实际网络并保存 YAML；不直接修改上游文件，不迁移旧 checkpoint。
- 新训练记录包含奖励非零频率、奖励均值曲线。拖动采样时间轴或点击奖励曲线，可联动选择采样帧。
- 奖励频率是**截至所选帧所有并行环境、所有环境步**的累计统计，分母为 `env_step × num_envs`；非零阈值是加权且含 dt 的贡献绝对值大于 `1e-8`。零权重项按官方逻辑不执行，原始值未知，不标为“从未触发”。原始值均值由启用时的加权贡献还原；上游已做 NaN/Inf 清理，不是清理前值。
- 奖励数据采用稀疏采样，最多约 400 组数据；频率在 GPU 上逐步累积。统计、渲染、序列化和浏览器传输均有开销，尚未做系统性能基准。指标每约 1.2 秒轮询，最新画面每约 0.5 秒独立轮询，不能视为每个仿真步即时展示。
- 老记录没有内部诊断数据时明确显示缺失，不补造数据。当前尚未提供任意奖励函数和触发条件的编辑入口；也未提供梯度视图、独立测试入口或任意项目的零配置运行。

`diagnostics.py` 的 PyTorch 奖励统计采集器不包含机器人名称、固定层宽或动作维度；`discovery.py` 只依赖标准库。官方奖励管理器的连接仍由 `microduck_bridge.py` 负责。


### 接入代码

- `rl_workbench/microduck.py`：独立训练进程与配置验证。
- `rl_workbench/microduck_bridge.py`：官方训练入口、日志/奖励采集与画面记录。
- `rl_workbench/static/microduck.*`：项目概览、环境定义、奖励函数与倍率、训练监控与采样回看。
- `.runtime/microduck_catalog.json`：从本地官方代码生成的任务目录、版本与设备信息。

### 本机验证记录

2026-10-08，在 RTX 5070 Laptop GPU 上分别完成官方默认奖励和 `action_rate_l2 × 2` 的 64 环境 × 5 迭代测试。每次记录 7,680 次交互、30 张同步采样图像、16 项奖励，actor / critic 观测分别为 61 / 76 维，动作为 14 维。检查了分项求和误差、官方 ONNX 的 61 维输入 / 14 维有限输出，并在独立短测试中验证暂停、继续、停止和 checkpoint 保存。另有 8 项自动化测试覆盖配置、生命周期与 CartPole 回归。其他 32 个注册任务尚未逐一进行训练验证。


奖励权重与屏蔽补充验证：临时目录内完成 64 环境 × 5 迭代，确认 action_rate_l2 固定为 -0.23、upright 屏蔽后权重与贡献均为零、实际计算计数为零。测试产物自动删除，不写入界面训练列表。

### 训练预算与整体奖励构成

迭代次数支持 1–100000；并行环境支持 16–4096，界面提供 64、256、512、1024、2048、4096。较大配置能否运行取决于显存与具体任务，选项开放不代表已做相应规模性能验证。迭代次数是 PPO 更新次数，不是单个回合的长度。

新训练额外统计与官方日志相同顺序的最近最多 100 个已结束回合，对各项加权奖励逐步累计，再取回合平均。整体奖励面板显示正贡献、负贡献、净总奖励与每项贡献。占比采用有符号的分项 / 净总奖励，因此正项可以超过 100%，负项可为负；净总奖励接近零时不显示百分比。官方总分与分项之和存在差额时单列，可能来源于额外奖励或浮点累计误差。原有 Episode_Reward 的归一化分项不参与这个分解。旧记录无法从稀疏采样准确还原这一统计，界面明确提示缺失。
